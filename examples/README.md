# Примеры входа и выхода

Результаты прогона пайплайна на синтетическом участке и четырёх объектах из набора «Пилотный проект 20 улиц». Все объекты посчитаны одной версией кода, с одним набором пород и без LLM-судьи, так что их можно сравнивать между собой.

- **Породы:** рябина `tree_rowan`, липа `tree_linden`, чубушник `shrub_mockorange`, сирень `shrub_lilac`.
- **Параметры:** стратегия `balanced`, одна итерация.

## Что в каждой папке

| Файл | Что это |
|---|---|
| `greening_layers.dxf` | Только слои результата `AI_GREENING_*` в координатах исходного чертежа. Подключается к генплану проектировщика внешней ссылкой, исходные слои не затрагиваются. |
| `report.json` | Файл интерпретации (ТЗ п. 8). Подробности ниже. |
| `input_synthetic_site.dxf` | Входной чертёж. Есть только у синтетического участка; входы пилотных объектов лежат в наборе данных кейса. |

**Слои в `greening_layers.dxf`:**

| Слой | Содержимое |
|---|---|
| `AI_GREENING_TREES`, `AI_GREENING_SHRUBS` | Посадки: блоки, в XDATA порода и `planting_id` для связи с отчётом |
| `AI_GREENING_ALLOWED_ZONE` | Где сажать можно |
| `AI_GREENING_EXCLUSIONS` | Зоны запрета, в XDATA `rule_id` |
| `AI_GREENING_REJECTED` | Отклонённые точки с причиной в XDATA |

**Что лежит в `report.json`:**
- `placements` — посадки с координатами и породой.
- `explanations` — для каждой посадки все проверки. В каждой проверке правило, фактическое и требуемое расстояние, статус, документ, пункт, дословная выдержка и страница PDF.
- `rejections` — почему отклонены точки-кандидаты, со ссылкой на норму.
- `regulatory` — итоговый статус и нормативное покрытие.
- `validation` — нарушения; во всех примерах их 0.

## Почему статус «требует проверки»

Нарушений нет ни в одном примере. «Требует проверки» (`NEEDS_REVIEW`) ставится, когда норма соблюдена, но её применимость нельзя подтвердить по данным чертежа. Таких причин три, и эксперт видит каждую в объяснении посадки:

1. **Липа с кроной 7 м.** Таблица 9.1 СП 42 рассчитана на деревья с кроной до 5 м; для более широкой кроны расстояния «следует увеличить», но на сколько, норма не говорит. Крона шире 5 м задевает сразу около 10 правил СП 42, поэтому на объектах с липами правил в статусе больше.
2. **Напряжение ЛЭП не указано в чертеже.** Знаки линий стоят у опор наружного освещения, поэтому принята линия до 1 кВ с зоной 2 м. Для линий выше 1 кВ зона шире.
3. **Сеть неопознанного типа.** Взят запас 2 м, но фактическая норма зависит от типа сети: у теплотрассы для части пород до 4 м (623-ПП п. 4.2.8).

Запас 3 м от существующих деревьев на статус не влияет: никакая норма его не задаёт, и проверять по НПА в нём нечего.

## Ограничения данных

- **Харьковский проезд.** LibreDWG не прочитал топоплан (`…00627tp.dwg`) и план наружного освещения (`НО_Харьковский проезд.dwg`); в составе пакета они помечены «не прочитан», для них нужен ODA File Converter. Файла «Бортовой камень.dwg» нет в пакете. Кроме того, в генплане есть копия контура границы работ в 5 км от плана; участком она не считается.
- **Багрицкого ул.** В пакете нет 15 файлов, на которые ссылается генплан, в том числе «Граница работ» и выгрузки ИРД.
- **Макеева С. ул.** Нет `xref_УО.dwg`. Посадок мало, потому что улица плотная: проезжая часть, бортовой камень, кабели и охранные зоны занимают почти всю свободную полосу.

## Как воспроизвести

1. Поднимите стенд (`docker compose up --build`, раздел 5 документации).
2. Упакуйте в ZIP папку объекта из набора «Пилотный проект 20 улиц»:
   - для Олимпийской деревни — `Исходные данные/10000176_Генплан_Олимп - Standard`;
   - для остальных — папку `Исходные данные` целиком.
3. Прогоните архив командами из раздела 5.3 [документации](../docs/DOCUMENTATION.md) с этими параметрами генерации:

```json
{"plantKinds": ["TREE", "SHRUB"],
 "speciesIds": ["tree_rowan", "tree_linden", "shrub_mockorange", "shrub_lilac"],
 "useLlmJudge": false, "maxIterations": 1}
```

Слои результата выгружаются через `GET /api/projects/{id}/export/dxf?layers=result`, отчёт — через `GET /api/projects/{id}/export/report`. Сводка по всем объектам лежит в `summary.json`.
